# Phase 3.1: Driver FE-TTLinker e Protocolo SCS — Context

**Gathered:** 2026-04-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Implementar `servo_hal`: driver de comunicação serial SCSCL para servos SCS0009 via FE-TTLinker.
**Esta etapa é somente leitura** — PING e READ de registradores. Nenhuma escrita de posição.
O objetivo é confirmar comunicação bidirecional confiável antes de qualquer movimento.

</domain>

<decisions>
## Implementation Decisions

### Linguagem e Stack
- **D-01:** C17 puro — sem C++, sem biblioteca Feetech (CLAUDE.md: componentes não-display = C17)
- **D-02:** Arquivo de componente: `components/nb_hal/servo_hal.c` + `servo_hal.h`
- **D-03:** CMakeLists via `idf_component_register` — componente `nb_hal` já existe

### Hardware (pré-definido em nb_hw_config.h)
- **D-04:** UART1, GPIO 20 (TX) / GPIO 33 (RX), 1Mbps — definidos como `NB_SERVO_PIN_TX/RX`, `NB_SERVO_UART_PORT`, `NB_SERVO_BAUD_RATE`
- **D-05:** Servo IDs: `NB_SERVO_ID_PAN = 1`, `NB_SERVO_ID_TILT = 2`
- **D-06:** FE-TTLinker cuida da conversão half-duplex — UART do ESP opera full-duplex normalmente (sem controle de direção no software)

### Protocolo SCSCL
- **D-07:** Formato de pacote (de SERVO_SAFETY.md):
  `[0xFF][0xFF][ID][LENGTH][INSTRUCTION][PARAM_1..N][CHECKSUM]`
  `CHECKSUM = ~(ID + LENGTH + INSTRUCTION + PARAMS) & 0xFF`
- **D-08:** Instruções a implementar nesta etapa: PING (0x01), READ (0x02)
- **D-09:** WRITE (0x03) e SYNC_WRITE (0x83) declarados no header mas **não testados** aqui — implementação adiada para 3.2/3.3
- **D-10:** Parser de response packet inclui validação de checksum — falha de checksum retorna `ESP_ERR_INVALID_CRC`

### Registradores a ler (Etapa 3.1)
- **D-11:** Present Position: addr 0x28, 2 bytes (0–4095)
- **D-12:** Present Load: addr 0x30, 2 bytes (indicador de torque)
- **D-13:** Present Temperature: addr 0x3F, 1 byte (°C)
- **D-14:** Present Voltage: addr 0x29 (byte adjacente à posição — verificar datasheet físico)
- **D-15:** Torque Enable: addr 0x18, 1 byte — apenas READ nesta etapa (para confirmar estado)

### Retry e Timeout
- **D-16:** Retry máx 3 por operação — definido no ROADMAP
- **D-17:** Timeout por operação: **calculado + margem** = `ceil(bits_por_pacote / baud_rate) + 2ms`
  A 1Mbps: pacote de 8 bytes ≈ 80µs TX + 80µs RX + latência servo ≈ <1ms; timeout fixo de **5ms** por tentativa é conservador e suficiente
- **D-18:** Após 3 falhas consecutivas: retorna `ESP_ERR_TIMEOUT`, não trava, não panic

### Concorrência
- **D-19:** Mutex FreeRTOS interno no `servo_hal` — callers não gerenciam lock
  Razão: safety task (20Hz) e boot init chamarão o HAL; mutex interno evita race sem exigir coordenação do chamador
- **D-20:** Mutex criado em `servo_hal_init()`, destruído em `servo_hal_deinit()`

### Estrutura de dados
- **D-21:** Sem estado cacheado no HAL — cada `servo_hal_read_*()` faz leitura real do hardware
  Razão: cache introduz staleness perigoso para safety layer; a safety task lê a 20Hz e quer valores frescos
- **D-22:** API por ID de servo: `servo_hal_ping(uint8_t id)`, `servo_hal_read_position(uint8_t id, uint16_t *out)`, etc.

### API Pública (header)
- **D-23:** Funções públicas com prefixo `servo_hal_`:
  - `esp_err_t servo_hal_init(void)`
  - `esp_err_t servo_hal_deinit(void)`
  - `esp_err_t servo_hal_ping(uint8_t id)`
  - `esp_err_t servo_hal_read_position(uint8_t id, uint16_t *out_pos)`
  - `esp_err_t servo_hal_read_load(uint8_t id, uint16_t *out_load)`
  - `esp_err_t servo_hal_read_temperature(uint8_t id, uint8_t *out_temp)`
  - `esp_err_t servo_hal_read_voltage(uint8_t id, uint8_t *out_voltage)`
  - `esp_err_t servo_hal_read_torque_enabled(uint8_t id, bool *out_enabled)`
  - `esp_err_t servo_hal_write_raw(uint8_t id, uint8_t addr, const uint8_t *data, uint8_t len)` — privado/interno, para 3.2+

### Logging
- **D-24:** Log em `DEBUG` para cada pacote enviado/recebido — desabilitado em produção
- **D-25:** Log em `WARN` para cada timeout de tentativa; `ERROR` após esgotar retries
- **D-26:** Módulo de log: `"servo_hal"` (prefixo ESP_LOG)

### Boot sequence
- **D-27:** `servo_hal_init()` chamado no `boot_manager` (fase de periféricos); PING obrigatório a ambos os IDs antes de retornar sucesso
- **D-28:** Falha de PING em boot: log de erro, retorna `ESP_FAIL` — boot_manager decide se é fatal ou degrado

### Claude's Discretion
- Implementação interna do buffer UART: tamanho do ring buffer de RX (256 bytes é suficiente para pacotes SCS, que são ≤16 bytes)
- Organização interna de funções helper (`nb_servo_build_packet`, `nb_servo_parse_response`) — privadas ao .c

</decisions>

## Existing Code Insights

- `components/nb_hal/`: componente já registrado no CMake — apenas adicionar `servo_hal.c` ao `SRCS`
- `components/nb_hal/nb_hw_config.h`: constantes de servo já definidas e prontas para uso

- `components/infra/error_policy.h`: macros `NB_ASSERT` disponíveis para validação de parâmetros

### Established Patterns
- Pattern de init/deinit: ver `sd_hal.c` — mesma estrutura de inicialização com ESP_ERROR_CHECK em init e log de status
- Pattern de mutex: ver `event_bus.c` — `xSemaphoreCreateMutex()` + `xSemaphoreTake/Give` com timeout
- Retorno de erro: sempre `esp_err_t`, nunca panic em runtime, `ESP_ERROR_CHECK` apenas em init

### Integration Points
- `boot_manager.c`: adicionar fase de init de servo HAL na sequência de boot (após infra, antes de services)
- `motion_safety` (Etapa 3.2): vai chamar `servo_hal_read_*` a 20Hz — API deve ser thread-safe (mutex interno garante isso)

<specifics>
## Specific Ideas

- Confirmar endereços de registrador contra datasheet físico do SCS0009 antes de finalizar — SERVO_SAFETY.md menciona que "podem variar entre revisões"
- Timeout de 5ms é conservador para 1Mbps; ajustar empiricamente se hardware mostrar latência maior
- FE-TTLinker não requer controle de direção via GPIO — apenas TX/RX normais da UART

</specifics>
